# 需求澄清指南

本指南用于在需求探索阶段进行有效的提问和澄清，确保在生成proposal和delta_spec之前，上下文完整且需求清晰。

---

## 核心立场

- **好奇心驱动，而非预设立场** - 提出自然出现的问题，不要遵循固定脚本
- **开放式探索，而非审问式** - 呈现多个有趣的方向，让用户跟随感兴趣的发现
- **可视化表达** - 善用ASCII图表来帮助澄清思路
- **自适应调整** - 跟随有趣的线索，当新信息出现时灵活转向
- **保持耐心** - 不急于下结论，让问题的形态自然显现
- **立足实际** - 必要时探索真实代码库，不要仅停留在理论层面

---

## 可执行的操作

根据当前情况，您可能需要：

### 探索问题空间
- 提出从用户描述中自然产生的澄清问题
- 挑战既有假设
- 重新定义问题
- 寻找类比帮助理解

### 探索代码库
- 绘制与讨论相关的现有架构
- 找到集成点
- 识别已使用的模式
- 揭示隐藏的复杂性

### 对比选项
- 头脑风暴多种方案
- 构建对比表格
- 勾勒出权衡取舍
- 推荐路径（如果用户询问）

## 需求澄清的时机

### 检查现有上下文

在开始时，快速检查已存在的内容：
- 查找 `docs/changes/` 目录下是否已有相同或相似需求的文档
- 使用 Glob 工具查找相关的 proposal.md、delta_spec.md 文件
- 查看相似需求的实现方式

### 当没有现成文档时

自由思考。当想法成熟时，可以向用户确认：
- "这个需求已经比较清晰了，需要我生成proposal吗？"
- 或者继续探索——不需要急于 formalize

### 当已有相关文档时

如果发现 `docs/changes/` 下已有相关需求：

1. **读取现有文档获取上下文**
   - `docs/changes/<需求id>/proposal.md`
   - `docs/changes/<需求id>/delta_spec.md`

2. **在对话中自然引用**
   - "您的设计提到使用XX，但我们发现YY可能更合适..."
   - "proposal中定义的范围是XX，但现在我们考虑..."

3. **在做出决策时提议记录**

   | 洞察类型               | 记录位置                          |
   |----------------------|---------------------------------|
   | 新需求发现            | 本次生成的proposal.md            |
   | 需求变更              | 本次生成的delta_spec.md          |
   | 设计决策              | 记录在proposal.md的影响分析章节  |
   | 范围变更              | proposal.md的"不在范围内"章节    |

   提议示例：
   - "这是一个设计决策。需要记录到proposal.md的影响分析中吗？"
   - "这改变了范围。需要更新proposal.md的'不在范围内'章节吗？"

4. **由用户决定** - 提出建议然后继续。不要施压。不要自动记录。

## 不需要做的事情

- 遵循脚本
- 每次都问相同的问题
- 产出特定的产物
- 得出结论
- 保持在同一个话题上（如果偏离有价值）
- 简洁（这是思考时间）

## 常见澄清问题示例

在需求澄清过程中，可以根据实际情况向用户提问：

### 关于需求本身
- "这个功能的核心用户场景是什么？"
- "这个需求要解决什么业务问题？"
- "现有的实现方式是怎样的？我可以查看相关代码吗？"

### 关于上下文关联
- "这个需求与项目中现有的哪些模块相关？"
- "有没有类似的实现可以参考？"
- "这次变更会影响哪些现有功能？"

### 关于边界条件
- "这个功能的边界条件是什么？"
- "如果遇到XX情况，应该如何处理？"
- "有哪些异常场景需要考虑？"

### 关于影响范围
- "这个功能是否涉及数据迁移？"
- "是否需要考虑向后兼容？"
- "有没有外部依赖需要关注？"

## 冲突点识别与澄清

除了模糊点，需求中还可能存在**冲突点**，需要识别并向用户确认。

### 冲突点的类型

#### 1. 需求内部矛盾
- 同一功能的不同描述相互矛盾
- 前置条件与后置结果不一致
- 多个业务规则相互排斥

**示例识别**：
```
需求描述：
- "用户可以在24小时内取消订单"
- "订单一旦支付成功，立即进入发货流程"

潜在冲突：24小时取消窗口与立即发货流程冲突
```

#### 2. 与现有设计冲突
- 新需求与现有架构设计不兼容
- 变更会影响现有功能的正常行为
- 违反了既有的业务规则或约束

**示例识别**：
```
现有设计：所有API调用都需要Token认证
新需求："开放某些API供匿名用户访问"

潜在冲突：安全策略变更
```

#### 3. 多方需求矛盾
- 不同角色/系统的需求相互矛盾
- 性能要求与功能完整性冲突
- 成本与功能的权衡

**示例识别**：
```
用户A需求：实时同步数据
用户B需求：保证数据一致性

潜在冲突：实时性 vs 一致性（CAP定理）
```

#### 4. 优先级冲突
- 多个功能的实现存在资源竞争
- 时间线相互冲突
- 依赖关系形成循环

**示例识别**：
```
需求1：P0优先级，必须本月上线
需求2：P0优先级，需要重构核心模块

潜在冲突：资源有限，如何安排开发顺序
```

### 冲突点的识别方法

1. **交叉验证**：对比需求描述与设计文档，检查一致性
2. **依赖分析**：分析需求之间的依赖关系，检查循环依赖
3. **角色分析**：从不同角色视角审视需求，检查矛盾点
4. **边界探测**：测试极端场景，检查边界条件是否冲突
5. **历史对比**：与已有的proposal/delta_spec对比，检查冲突

### 冲突点澄清的提问方式

当识别到潜在冲突时，可以这样提问：

```
我注意到一个潜在冲突：
- 需求A提到"XXX"
- 需求B提到"YYY"

这两者在[具体场景]下似乎存在矛盾。
请问您希望如何处理？
```

或者：

```
这个需求与现有设计存在冲突：
[现有设计描述]
[新需求描述]

选项1：调整新需求以适配现有设计
选项2：重构现有设计以支持新需求
选项3：[其他方案]

您倾向于哪个方向？
```

### 冲突点记录

当冲突无法立即解决时，建议记录在proposal.md中：

```
## 待解决冲突

| 冲突点 | 涉及需求/模块 | 状态 | 备注 |
|--------|--------------|------|------|
| XXX    | 需求A vs 需求B | 待确认 | 需要XX决策 |
```

## 模糊点 vs 冲突点 对比

| 特征 | 模糊点 | 冲突点 |
|------|--------|--------|
| 本质 | 信息不完整 | 逻辑矛盾 |
| 表现 | 说不清楚 | 说清楚了但互相矛盾 |
| 处理方式 | 补充信息 | 确认优先级或调整方案 |
| 解决标志 | 用户补充了缺失信息 | 用户选择了解决路径 |
| 常见提问 | "具体是指...？" | "A和B矛盾，您希望优先哪个？" |

## 结束探索

探索不一定有固定的结束方式。可能：

- **转化为proposal**："准备好了吗？我可以生成proposal.md和delta_spec.md。"
- **提供清晰度**：用户得到了需要的东西，继续推进
- **稍后继续**："我们可以随时继续"

当感觉事情逐渐成形时，您可以总结：

```
## 我们得出的结论

**问题**：[清晰的理解]

**方法**：[如果有的话]

**开放问题**：[如果有的话]

**下一步**（如果准备好了）：
- 生成proposal.md和delta_spec.md
- 继续探索：继续对话
```

但这个总结是可选的。有时候思考本身就是价值。

## 提问原则

- **不要实现** - 不要写代码或实现功能。可以生成proposal和delta_spec，但不要写应用代码
- **不要假装理解** - 如果有不清楚的地方，深入挖掘
- **不要仓促** - 探索是思考时间，不是任务时间
- **不要强制结构** - 让模式自然浮现
- **不要自动记录** - 提议保存洞察，不要直接去做
- **要可视化** - 一个好的图表值得很多段落
- **要探索代码库** - 将讨论立足于现实
- **要质疑假设** - 包括用户的和AI自己的
