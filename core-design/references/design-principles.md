# Design Principles Reference: core-design

**Skill**: core-design
**Usage**: 本文档由 SKILL.md Phase 2 通过 GATE 加载，Agent 在生成 delta_design.md 时必须遵守以下原则。每条原则包含约束描述、触发条件、违反后果、与 delta_design 章节的映射。

---

## P-1: 架构一致性

### 约束
- 增量代码必须锚定现有架构层次：新增模块必须在全局 design.md 定义的分层架构中找到自己的位置，不能凭空出现不属于任何层的模块
- 修改不跨越模块边界：修改模块 A 时不能把本该属于模块 B 的职责塞进模块 A，模块边界由全局 design.md 定义
- 新增代码归入现有文件体系：常量归常量文件、工具函数归工具模块、配置归配置模块、数据结构体扩展归定义该结构体的现有文件

### 触发条件
始终生效

### 违反后果
破坏现有架构一致性，导致后续维护和扩展困难；代码审查阶段会被打回

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 锚定现有层次 | 二、系统架构 2.1 | 新增模块在架构图中标注所属层次 |
| 不跨越边界 | 二、系统架构 2.2 | 每个模块的"职责"列不得包含属于其他模块的功能 |
| 归入现有文件 | 三、详细设计 3.1 | 每个模块设计中列出"文件归属"：新代码放在哪个现有文件中 |

---

## P-2: 入口出口明确

### 约束
- 每个设计章节必须声明触发入口：增量代码从哪个已有入口（API endpoint、事件监听、定时任务、配置加载、hook 回调等）触发
- 每个设计章节必须声明输出出口：代码执行后结果写到哪里（返回值、数据库、消息队列、事件、日志），下游消费方是谁
- 如果现有代码没有天然接入点，设计方案必须包含对现有代码的最小改造（如新增 hook、回调注册点），禁止设计出无调用方的"孤岛代码"

### 触发条件
始终生效

### 违反后果
产出不可落地的设计——代码实现阶段无法确定代码该写在哪里、由谁调用；形成死代码

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 声明触发入口 | 三、详细设计每个子节 | 每个子节包含"触发入口"字段 |
| 声明输出出口 | 三、详细设计每个子节 | 每个子节包含"输出出口"字段 |
| 无入口需设计集成 | 五、设计决策 | 新增一条决策：集成方案（含对现有代码的最小改造） |

---

## P-3: 最小变更影响

### 约束
- 修改范围最小化：只改实现需求所必须的代码路径，不附带"顺手重构""顺便优化"
- 新增优先于修改：能通过新增文件/函数/类实现的，不修改现有文件
- 变更影响面必须可枚举：每个设计章节必须列出"受影响的现有代码"（文件路径 + 函数名），不能笼统说"影响 XX 模块"

### 触发条件
始终生效

### 违反后果
变更范围不可控，回归测试无法聚焦，引入不相关缺陷

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 修改范围最小化 | 十四、风险与对策 | "变更范围蔓延"作为风险项列出 |
| 新增优先于修改 | 五、设计决策 | 涉及修改现有文件的决策必须说明不可新增的理由 |
| 影响面可枚举 | 三、详细设计每个子节 | 每个子节包含"受影响代码"字段（文件路径 + 函数名） |

---

## P-4: 接口契约向后兼容

### 约束
- 新增字段/参数必须可选或提供默认值：不能因新增需求把原有调用方破坏
- 修改接口必须声明兼容策略：如必须改接口，需明确版本化（v1/v2）、双写过渡、还是直接切换
- 删除接口必须提供迁移路径：REMOVED 的接口必须有调用方迁移方案和时间线

### 触发条件
设计涉及新增/修改/删除对外接口时

### 违反后果
破坏现有调用方，导致线上故障；接口变更无迁移方案导致部署窗口不可控

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 新增字段可选 | 三、详细设计 3.2.2 | 接口详情中新增参数的"必填"列标注为"否"并提供默认值 |
| 兼容策略 | 三、详细设计 3.2.2 | 修改接口时增加"兼容策略"子节 |
| 迁移路径 | 三、详细设计 3.2.2 | 删除接口时增加"迁移路径"子节 |

---

## P-5: 异常路径与降级完整性

### 约束
- 每个外部依赖必须有降级策略：调用的外部服务/数据库/第三方 SDK，必须设计超时、重试、熔断、兜底返回
- 每个核心流程必须有失败路径设计：不仅设计 happy path，还必须设计关键步骤失败后的回滚/补偿/告警路径
- 异常不能静默吞没：任何 catch/错误处理必须要么传播、要么记录日志、要么兜底返回明确值

### 触发条件
设计涉及外部服务调用、数据库访问、第三方 SDK、跨模块调用时

### 违反后果
实现阶段遇到外部依赖故障时无降级可用，导致级联失败；线上问题无法定位

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 外部依赖降级 | 十一、异常处理设计 11.2 | 列出每个外部依赖的降级策略 |
| 失败路径 | 六、核心流程设计 6.1 | 时序图包含 alt/else 异常分支 |
| 异常不吞没 | 十一、异常处理设计 11.3 | 错误码表覆盖所有可预见异常 |

## P-6: 可测试性内建

### 约束
- 外部依赖必须可注入/Mock：依赖外部服务、数据库的模块必须通过接口/参数注入，不能硬编码依赖实例
- 设计必须包含验证方式：每个详细设计子章节必须说明"如何验证这个设计是正确的"，关联到 delta_test_design.md 的具体 TC
- 状态必须可重置：涉及状态修改的设计，必须提供状态重置/清理方式，确保测试隔离

### 触发条件
始终生效

### 违反后果
实现后无法编写有效的单元测试；测试依赖外部环境，不可重复执行

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 可注入 | 三、详细设计 3.1 | 核心模块设计中标注"可注入点"（接口/参数） |
| 验证方式 | 三、详细设计每个子节 | 每个子节包含"验证方式"字段，关联 delta_test_design.md 的 TC ID |
| 状态可重置 | 三、详细设计 3.1 | 状态管理模块设计中包含"重置方式" |

## P-7: 依赖管控

### 约束
- 依赖方向必须单向无环：模块 A 依赖 B，B 不能反向依赖 A；出现循环依赖时必须通过接口抽取或事件解耦
- 新增第三方依赖必须有充分理由：项目中已有同类功能的依赖时优先复用；引入新依赖必须在设计决策中说明已有依赖为何不满足
- 依赖范围最小化：只依赖需要的子模块，不引入整个包/框架

### 触发条件
设计涉及新增模块间依赖或新增第三方依赖时

### 违反后果
循环依赖导致编译/启动失败；依赖膨胀导致安全漏洞和升级困难

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 单向无环 | 二、系统架构 2.2 | 模块划分的"依赖模块"列不得出现双向依赖 |
| 新增依赖理由 | 七、技术选型 7.1 | 每个新增依赖必须有"选型理由"和"已有替代方案不满足原因" |
| 依赖范围最小 | 七、技术选型 7.1 | 选型清单中注明引入的具体子模块 |

## P-8: 安全默认

### 约束
- 默认拒绝，显式授权：新增接口默认无权限访问，必须显式声明需要的权限
- 外部输入必须校验：所有来自 API 参数、配置文件、消息队列的外部输入必须校验类型、范围、长度
- 敏感数据必须标记处理方式：设计中涉及的密码、密钥、个人信息必须标注存储加密/传输加密/日志脱敏策略

### 触发条件
设计涉及新增接口、处理外部输入、涉及敏感数据时

### 违反后果
安全漏洞；数据泄露；合规风险

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 默认拒绝 | 八、安全设计 8.1 | 每个新增接口标注认证要求 |
| 输入校验 | 三、详细设计 3.2.2 | 接口参数表增加"校验规则"列 |
| 敏感数据 | 八、安全设计 8.2 | 列出涉及的敏感数据及加密/脱敏方式 |

---

## P-9: 可观测性内建

### 约束
- 关键业务节点必须埋日志：核心流程的入口、出口、关键决策点、异常点必须有日志
- 性能指标必须可采集：性能目标对应的指标必须有具体的采集方式和采集点
- 跨模块调用必须可追踪：跨服务/跨模块的调用链必须有 trace ID / correlation ID 传递机制

### 触发条件
始终生效

### 违反后果
线上问题无法定位；性能瓶颈无法发现；故障排查依赖猜测

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 埋日志 | 六、核心流程设计 6.1 | 时序图关键步骤标注日志级别 |
| 指标可采集 | 九、性能设计 9.1 | 性能目标表增加"采集方式"列 |
| 链路可追踪 | 十二、监控与日志 12.3 | 明确 trace ID 传递方案 |

---

## P-10: 数据变更安全

### 约束
- DDL 变更必须可回滚：每个 DDL 语句必须有对应的回滚 SQL
- 数据迁移必须可验证：迁移脚本执行后必须有验证步骤（行数比对、抽样校验）
- 破坏性变更必须分步执行：删表、改字段类型等必须分"创建新结构 → 迁移数据 → 切换 → 清理旧结构"多步完成

### 触发条件
设计涉及数据库 DDL 变更或数据迁移时

### 违反后果
数据丢失；迁移失败无法回滚；生产事故

### 与 delta_design 章节的映射

| 原则子项 | 必须体现的章节 | 体现方式 |
|----------|---------------|----------|
| 可回滚 | 三、详细设计 3.3.3 | 每条 DDL 后附带回滚 SQL |
| 可验证 | 三、详细设计 3.3.3 | 迁移方案包含验证步骤 |
| 分步执行 | 三、详细设计 3.3.3 | 破坏性变更分步骤描述，标注执行顺序 |
