# 云见 Skill 建议驱动进化

## 组织输入

1. 从已获得的改进建议开始，确认建议对应的 Skill、原有正式内容以及本轮修改目标和范围。缺少对应关系或原内容时先补齐，不凭同名猜测。
2. 使用同一流程处理 SDD 和其他场景来源的 Skill；不要求先执行一次查找使用。
3. 仅修改对应 Skill。经验不是本流程的审核变更对象；前置评测和建议生成不在本流程展开。
4. 读取实际可用的 Skill 广场操作指引或接口约定，不编造提交、审核或发布命令。渠道不可用时保留候选和说明，明确“尚未提交审核”，待渠道恢复后提交；不得用本地保存代替广场审核。

## 生成可审核的候选版本

以原 Skill 为基础，根据建议进行有范围的修改，生成独立的候选版本。正式 Skill 在审核和正式变更成功前继续使用原内容。

随候选版本提供：

- 修改内容及其对应的建议；
- 每项修改预期带来的改进；
- 未采纳的建议及原因（如有）；
- 建议有歧义、与现有能力冲突或无法落实的情况，供用户判断。

保留原 Skill、建议、候选内容和说明之间的关联，按既有机制标识本轮确切候选内容，不另行规定版本管理实现。不能将“Agent 修改完成”表述为“正式 Skill 已更新”。

## 提交 Skill 广场审核

将候选版本和修改说明提交到 Skill 广场，形成关联建议、原 Skill 与候选版本的待审核记录。确认用户可在同一审核界面查看原内容、建议、前后差异和说明。

核实提交结果；提交失败时明确尚未进入审核。由用户判断修改是否正确落实建议、符合 Skill 定位、包含不必要的改动。

| 用户审核结果 | Agent 后续动作 |
|---|---|
| 通过 | 确认通过的是哪一份确切候选内容，再进入正式变更 |
| 退回修改 | 将原建议、审核意见和当前候选版本共同作为输入，继续修改并更新说明，重新提交审核 |
| 拒绝 | 结束本次进化，保留原有正式 Skill，不再发起正式变更 |
| 待审核 / 结果未知 | 保留待审核状态，不将其当作通过 |

退回后的用户审核对象必须是最新候选版本；之前轮次的通过或意见不能代替新一轮审核。

## 正式变更与核验

1. 仅在用户于 Skill 广场审核通过后，通过广场正式变更流程应用审核通过的确切候选内容。
2. 在生效前核对候选内容与实际获批内容一致。审核后候选发生任何修改，必须重新提交审核；原正式 Skill 已发生变化而使本轮审核依据失效时，也需重新核对并审核。
3. 核实正式变更结果及生效内容与获批候选一致。保留建议、修改说明、审核结论与正式变更的关联，供后续追溯。
4. 将“审核通过”和“正式变更完成”分别报告。正式变更失败或结果未知时，明确“尚未确认生效”，保留实际状态和失败原因；不要宣称更新成功，也不要用未审核的其他内容替换。
5. 正式变更完成后，后续任务通过 [yunjian-skill-use](../yunjian-skill-use/SKILL.md) 的查找与获取流程使用更新后的 Skill。已有项目本地内容不因广场变更自动覆盖，由项目后续获取或更新流程处理。
